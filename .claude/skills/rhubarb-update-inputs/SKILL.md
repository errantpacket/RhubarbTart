# Updating RhubarbTart's pinned inputs

Everything an image is made of is pinned in two committed files. Updating means re-deriving
those pins from upstream, with the tools' cross-checks intact, then having a human review the diff:

| File | Pins | Regenerated by |
|---|---|---|
| `sources.lock.json` | IPSW, Chrome, ZAP, Perimeter 81: URL, sha256, version, signer | `uv run tools/resolve.py resolve` (Mac only) |
| `config/toolchain.env` | tart, packer, packer-plugin-tart, uv: URL + sha256 | `uv run tools/resolve.py toolchain-pin [--latest]` (any OS with gpg) |

What to track, and what signer to expect, is hand-edited in `config/sources.json`. The review
step is the point of the design: a pin is only as trustworthy as the person who approved the
diff. Always show the user what changed and why it's plausible. Never commit a lock change
without that.

Hand-editing a hash or URL in either pin file bypasses the checks that produced it, so don't.
If a value looks wrong, regenerate it and investigate the difference.

## Refresh image inputs (macOS 26.x + apps)

```sh
source scripts/env.sh && uv run tools/resolve.py plan      # preview: no downloads, any OS
source scripts/env.sh && uv run tools/resolve.py resolve   # Mac: download + verify + write lock
git diff sources.lock.json
```

Review the diff against this checklist, and summarize it for the user:

- **macOS**: is the `build`/`version` change expected (a newer 26.x)? Is `url` on
  `updates.cdn-apple.com`? Does `hash_sources` list both the Apple CDN and ipsw.me? A new
  build also means `REBUILD_VANILLA=1` on the next build, and the Setup Assistant
  `boot_command` may need re-validation.
- **Each app**: is the version bump plausible (release notes exist)? Is `signature.team_id`
  unchanged and equal to `config/sources.json`? Is `notarized` true? Is the `signer` string the
  same vendor as before?
- **Chrome**: `version` vs `advertised_version`. A small lag is normal during a rollout.
- Unexpected churn (sizes jumping wildly, a new signer, URL host changes) is a stop-and-ask.

Then commit the lock (with the user's go-ahead) and build (the `rhubarb-build` skill). The VM
name changes whenever the artifact hashes change. That's intended: the name identifies the inputs.

**Freeze macOS**: set `"pin_build": "25G83"` (for example) under `macos` in
`config/sources.json`. Apps still refresh on resolve.

## Pin vendor Team IDs (first run, or when warned)

`team_id: null` means "record and warn". resolve prints the observed ID and signer. Before
pinning, confirm it out-of-band (vendor docs, a previously trusted install's
`codesign -dv`/`pkgutil --check-signature` output, the vendor's support). Pinning the value
you just downloaded, without checking, only records it. Then set it in `config/sources.json`
(apps) or `TART_TEAM_ID` / `PACKER_TEAM_ID` in `config/toolchain.env`. Once pinned, a signer
change fails the build loudly.

## Bump the host toolchain

```sh
uv run tools/resolve.py toolchain-pin --latest   # needs gpg; fine to run on Linux
git diff config/toolchain.env
./tools/check.sh                                 # flags plugin version drift in packer/*.pkr.hcl
```

- `toolchain-pin` only accepts a hash when two upstream views agree (the release's checksums
  file vs GitHub's asset digest; HashiCorp SHA256SUMS vs its GPG signature from the key in
  `config/keys/`). If it refuses, report why; don't work around it.
- If the plugin version changed, update `version = "= X"` in both `packer/*.pkr.hcl` files.
- On the Mac, run `./tools/bootstrap.sh` then `preflight`. A Tart or plugin bump can change
  build behavior, so recommend a full build before relying on it.
- If the release location moved (as Tart did from cirruslabs to openai), update the URL
  allow-list in `tools/bootstrap.sh` and the repo names in `cmd_toolchain_pin` together, and
  tell the user. A move is a provenance event worth a sentence in the README.

## New macOS major (e.g. 27)

This is a project, not a refresh. Set `macos.major` in `config/sources.json`, and expect to:
- rework the Setup Assistant `boot_command` (start from upstream cirruslabs/macos-image-templates
  for that release);
- rename the `rbt-tahoe-` prefix in `scripts/build.sh`;
- re-check the output strings asserted in `guest/finalize.sh` and `scripts/smoke-test.sh`;
- update the README.

Hand the code-change part to the `rhubarb-dev` skill.

## Add or remove an app

Read `references/adding-an-app.md`. It covers the resolver, config entry, guest post-install
verification, and README updates. Removing an app is the reverse: drop the `config/sources.json`
entry and its case in `guest/install.sh`'s post-install loop, update the README tables, re-resolve.
