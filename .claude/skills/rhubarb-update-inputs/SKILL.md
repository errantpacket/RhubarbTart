# Updating RhubarbTart's pinned inputs

Everything a guest is made of is pinned in committed files, re-derived by tools that cross-check
upstream, and approved by a human reviewing the diff. That review is the point of the design: a
pin is only as trustworthy as the person who approved it. Always summarize what changed and why
it's plausible. Never commit a lock change without that.

| File | Pins | Regenerated by | Runs on |
|---|---|---|---|
| `locks/<profile>.lock.json` | OS image, nixpkgs (NixOS), packages: URL, sha256, version, signer | `uv run tools/resolve.py resolve <profile>` | macOS profiles: a Mac. NixOS/Kali: any OS with gpg |
| `config/toolchain.env` | tart, packer, plugin, uv | `uv run tools/resolve.py toolchain-pin [--latest]` | any OS with gpg |

What to build is hand-edited: `profiles/*.json`, `config/bases/*.json` and `config/packages/*.json`
(sources, expected Team IDs, key files + fingerprints). Hand-editing a *hash* or *URL in a lock*
bypasses the checks that produced it, so don't. Regenerate it and investigate any difference.

## Refresh a profile

```sh
uv run tools/resolve.py plan <profile>                 # preview, no downloads
uv run tools/resolve.py resolve <profile> [--skip-large]   # --skip-large: don't fetch OS images now
git diff locks/<profile>.lock.json
```

Review against this checklist and summarize it for the user:

- **Base image:**
  - **macOS:** a newer build of the *same* major; URL on `updates.cdn-apple.com`; `hash_sources`
    lists Apple's CDN and ipsw.me. A new build gets a new vanilla VM automatically (its name
    includes the build), so no `REBUILD_VANILLA` is needed. Do re-check the keystroke flow (26)
    on the next build, and delete the old vanilla VM when it's no longer needed.
  - **NixOS:** new `release` and `nixpkgs.rev` that belong together (the ISO name contains the
    short rev); `nar_sha256` present.
  - **Kali:** new `version`; `hash_sources` says signed by `827C8569…`.
- **Each package:**
  - The version bump is plausible (release notes exist).
  - macOS: `notarized` is true, and `signature.team_id` matches the pinned value in
    `config/packages/<id>.json`. Where that pin is still `null` (ZAP, Perimeter 81 until pinned),
    compare with the previous lock instead: a change there is a signer change.
  - apt `.deb`: `hash_sources` names the expected key fingerprint.
  - TOFU entries (`tofu:` in `hash_sources`) deserve a closer look, because nothing upstream
    vouched for their hash: Chrome and WARP on macOS, Perimeter 81, and the nixpkgs tarball.
    The nixpkgs tarball is still pinned by git commit, and its NAR hash is re-checked by Nix in
    the guest.
- **Stop and ask** about unexpected churn: a new signer, a URL host change, wild size jumps, or
  a package moving from vendor-signed to TOFU.

Then commit (with the user's go-ahead) and build (`rhubarb-build` skill). The VM name changes
whenever inputs change. That's intended: the name identifies the inputs.

**Freeze an OS:** set `ipsw.pin_build` (macOS) or `kali.pin_version` (Kali) in the base. For
NixOS, keep the lock: its `nixpkgs.rev` is the freeze.

## Pin Team IDs and keys

- `team_id: null` means "record and warn". resolve prints the observed ID. Confirm it out-of-band
  (vendor docs or support, a previously trusted install's `codesign -dv`) before pinning it in
  `config/packages/<id>.json`. `TART_TEAM_ID` / `PACKER_TEAM_ID` live in `config/toolchain.env`.
- **Signing-key rotations are a hard stop, not a routine bump:** a vendor apt key, the Kali
  archive key (rotated in 2025) or a Tailscale distsign root. Fetch the new key from the vendor
  over HTTPS, compare its fingerprint with a second source (vendor docs, keyserver, release
  notes), then add it to `config/keys/` and update **both** `key` (the filename) and `key_fpr`.
  Explain this to the user.

## Bump the host toolchain

```sh
uv run tools/resolve.py toolchain-pin --latest    # gpg needed; any OS
git diff config/toolchain.env && ./tools/check.sh # check.sh flags plugin-version drift
```

- It only accepts a hash when two upstream views agree. If it refuses, report why; don't work around it.
- After committing, re-run `./tools/bootstrap.sh` on the Mac. Until then preflight fails with
  "config/toolchain.env changed since the last tools/bootstrap.sh", which is intended.
- A plugin bump means updating `version = "= X"` in every `packer/*/*.pkr.hcl`.
- A Tart/plugin bump can change build behavior, so recommend a full build of each family.

## Add tools or OS bases

Read `references/adding-inputs.md`: a new tool (package variants, maybe a resolver), or a new OS
base or release (usually code too: use `rhubarb-dev`). New *profiles* built from the existing
catalog belong to the `rhubarb-profiles` skill. Removing a tool means dropping it from the
profiles and deleting its package file, then re-resolving the affected profiles.
